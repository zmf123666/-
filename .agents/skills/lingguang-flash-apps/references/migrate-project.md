# 迁移已有项目

用户要求把已有 Web 或 React 项目改造成灵光闪应用时，完整读取本文档。默认采用隔离迁移，禁止直接把脚手架覆盖到已有项目中。

## 盘点原项目

1. 确认用户的迁移目标、原项目目录和输出目录。输出目录默认选择在原项目旁边，且必须尚不存在。
2. 读取原项目适用的 `AGENTS.md`（如有），检查 Git 状态和未提交改动，不得覆盖或丢弃用户现有修改。
3. 盘点入口、路由、Provider、业务组件、样式、依赖、锁文件、静态资源、环境变量、网络请求、持久化和浏览器 API。
4. 识别远程资源、前端密钥、不受支持的依赖和宿主能力差异，并记录迁移风险。

## 创建隔离迁移目标

迁移目标不存在时，返回总 `SKILL.md` 的渐进式路由，再完整读取 `references/create-project.md`，按官方流程新建迁移目标。不要自行复制脚手架、改用仓库分支或把脚手架解压到原项目上。

迁移目标建立后，完整读取其中的 `AGENTS.md`，并按原项目实际使用的能力只读取必要的 `docs/API_*.md`。

## 执行迁移

1. 保留脚手架的平台入口 `src/main.tsx`、`package.json`、锁文件、构建配置和插件。把原项目的业务组件、Provider、样式和资源迁入 `src/App.tsx` 及业务模块，不要复制原项目入口覆盖平台入口。
2. 只使用脚手架 `package.json` 已声明的依赖。原项目依赖不在脚手架中时，优先使用现有依赖或平台能力改写；禁止擅自安装新依赖。
3. 无法使用现有依赖等价改写时，向用户说明缺失能力、影响范围和可选方案，取得用户取舍后再继续。
4. 把远程资源、环境变量、网络请求、存储和浏览器能力逐项改造成符合脚手架 `AGENTS.md` 与相关 `docs/API_*.md` 的实现。
5. 按宿主能力要求迁移相机、相册、陀螺仪、LLM、搜索等能力。禁止假设普通浏览器 API 在 App WebView 或 iframe 中一定可用。
6. 禁止把密钥、访问令牌、Cookie 或仅适用于原环境的私密配置迁入前端源码。
7. 在项目根目录维护 `manifest.json`；以脚手架中的 `plugins/manifest-utils.ts` 和 `plugins/vite-plugin-validate-manifest.ts` 为字段、封面格式和路径规则的事实来源。

## 完成迁移

完成业务迁移和关键路径实现后，把新目录作为改造结果交付。除非用户明确要求且原项目已有可恢复的版本控制保护，否则不要原地覆盖旧项目。

用户要求构建、质检、打包、预览或正式发布时，再按总 Skill 路由完整读取 `references/build-and-release.md`；不要在迁移阶段提前加载发布流程。
